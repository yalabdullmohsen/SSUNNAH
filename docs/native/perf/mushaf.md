## ما تبيّن
- **الخطوط مضمَّنة في الحزمة (`Data/mushaf/fonts/p{n}.ttf`) وليست مُنزَّلة**: لا زمن تنزيل ولا استئناف؛ بند «تنزيل على دفعات» غير منطبق على البنية الحالية (156MB داخل الحزمة).
- مسار البيانات سريع أصلًا؛ العنق الحقيقي في طبقة العرض: `MushafPageView.init` يقرأ الخط والصفحة **على الخيط الرئيسي** عند كل إعادة تقييم لـ`body` القارئ، و`TabView` يحمل 604 ابنًا.
- سلاسة التقليب (إطارات ضائعة) تُقاس على المحاكي/الجهاز بـInstruments؛ لم تُقَس هنا (لا يُدّعى رقمها).

## بعد #3201 (LRU للصفحات/التخطيط + تحميل مسبق ±2 في الخلفية)
القياس: `MushafPerfTests.testAfterCache` (سطر `MUSHAF_PERF_AFTER`)؛ تقليب كل 120ms مع prefetch، مرّتان (الضجيج بين التشغيلين ظاهر).

- الذاكرة لا تنمو مع التقليب: الحد 24 صفحة، والهبوط عن القيمة الأولية بسبب تحرير بيانات الفهرس/الصفحات المؤقتة وقت القياس.

- **الإطارات الضائعة الفعلية لم تُقَس** (تحتاج Instruments على المحاكي/الجهاز) فلا أدّعي رقمها؛ وبالتالي لا مسوّغ قياسيًّا لاستبدال `TabView` الآن، ويبقى كما هو.

## فتح الشاشة والبحث (ن3، 2026-10-15)
- **السبب الجذري:** `MushafScreen` كان يبني `MushafSearch` (114 ملف JSON + تطبيع) متزامنًا على الخيط الرئيسي داخل `.task` (macOS debug: 4358 ms)، ويبحث بمسح خطي لكل استعلام (حتى 615 ms).
- **الإصلاح:** فهرس بايتات مسبق الحساب (`memmem` + بحث ثنائي) يُبنى متوازيًا وخارج الخيط الرئيسي؛ تُعرض الصفحة فور جاهزية المستودع والفهرس، ويلتحق البحث لاحقًا.
- القياس (`MushafPerfTests.testSearchBaseline`، macOS debug): بناء 4358 → 166 ms؛ الاستعلامات 0.2–2.3 ms (كانت حتى 615)؛ استعلام بلا نتيجة 482 → 1.9 ms؛ النتائج مطابقة للمسح الخطي (تسعة استعلامات).
- **المحاكي (n3-sim، iOS 26.5، `MUSHAF_PERF` في السجل، فئة `mushaf-perf`):** `screen_task_start` ← `repo_index_ready` +0.37 s ← `search_ready` +1.2 s بعدها. الصفحة تُرسم قبل جاهزية البحث. افتتاح التطبيق نفسه (IntroPolicy) ≈1.6 s، فالوصول للمصحف ≈2.5 s من الإطلاق (الهدف < 3 s).
- رقم 23 s في `MushafFlipHitchUITests` ليس زمن التطبيق: هو `app.launch()` (انتظار خمول XCUITest) ولم يتغيّر بعد إصلاح البحث؛ فلا يُعتمد.
- **التقطيع:** `swipeRight` في XCUITest يقيس زمن حقن اللمسة لا زمن الإطار، ولم ينتج xcresult مقياس `XCTHitchMetric`؛ فلا رقم صالحًا بعد ولا ادعاء.

## تقطيع التقليب داخل التطبيق (ن3، 2026-10-15)
- **القياس:** `scripts/mushaf-flip-hitch.sh [N] [START]` يبني Debug ويطلقه بـ`-mushafAutoFlip N`؛ `Mushaf/MushafFlipProbe.swift` (DEBUG فقط) يقلّب N صفحة ويقيس فواصل `CADisplayLink` داخل نافذة كل تقليبة ويصدر signpost باسم `flip` وسطر `MUSHAF_HITCH`. (أرقام XCUITest السابقة غير صالحة.)
- **السبب الجذري:** `sample` على الخيط الرئيسي: ~60% من الوقت في تحديث رسم SwiftUI (`PreferenceCombiner`) و~28% في رسم الغلايفات. `MushafPageView.init` ≤4.2ms و`pageLayout` ≤21ms فليسا السبب. السبب: كل كلمة (≈450 عقدة لكل صفحة × 3 صفحات مرسومة) تحمل إيماءتي نقر/ضغط مطوّل وتسمية وصول.
- **الإصلاح:** الإيماءات على الصفحة الحالية فقط (`interactive: n == current`، `including: .none` للجارتين) دون تغيير الشكل؛ الحارس البصري ينجح (12 لقطة).
- **قبل → بعد (50 تقليبة، Debug على n3-sim):** p95 225.7 → 29.0 ms؛ الأقصى 440.8 → 165.3 ms؛ إطارات رُسمت 572 → 1006. المتبقي ≈1 خطوة >33ms لكل تقليبة (إنشاء الصفحة الجديدة)؛ الهدف p95<8ms لم يتحقق في Debug على المحاكي، ويلزم قياس Release/جهاز. تسمية الوصول ما زالت على كل كلمة (إزالتها مع الإيماءات خفّضت p95 إلى ≈28.5 فقط، فأثرها بعد الإصلاح ضئيل).
- **Release (2026-10-15):** `CONFIG=Release scripts/mushaf-flip-hitch.sh` يبني Release بعلم `-DMUSHAF_PROBE` (المسبار يعمل بـDEBUG أو MUSHAF_PROBE). قبل أي إصلاح جديد: p95 28.75 ms، الأقصى 245.4، 49/50 تقليبة >33ms — أي أن Release لا يختلف عن Debug، فالسبب عمل ثابت لكل تقليبة لا نقص تحسين.
- **القياس الموزَّع:** سجل hit/miss لكاش التخطيط أظهر أن `prefetch` يحسب التخطيط بحجم الحاوية (402×778) بينما الصفحة تطلبه بـ402×874، فكان كل تخطيط يُحسب مرة ثانية **على الخيط الرئيسي** (≈66 إخفاقًا في 50 تقليبة). الإصلاح: `MushafRepository.noteRenderSize` يسجّل الحجم الفعلي والتحميل المسبق يستعمله → إخفاقات الرئيسي 66 → 0. والخط والـJSON كانا محمّلين مسبقًا أصلًا فليسا السبب.
- **TabView:** `ForEach(1...604)` يُعاد تقييمه كله لكل تقليبة؛ استُبدل بنافذة ±2 حول الصفحة الحالية (الصفحة 150 تظهر سليمة بعد 50 تقليبة، والحارس ينجح).
- **بعد (50 تقليبة، Release):** p95 28.75 → 26.6 ms؛ الأقصى 245.4 → 108.7؛ 49/50 تقليبة ما زالت >33ms. الهدف p95<8ms لم يتحقق: المتبقي بناء ≈450 `Text` لصفحة جارة جديدة في كل تقليبة (SwiftUI)؛ الحل المرشح تجميع كلمات السطر في نص واحد للجارتين، ويحتاج حارسًا بصريًا صارمًا.
- **ملاحظة:** `-snapshotRoute` يعمل في DEBUG فقط (`SunnahApp.swift` ملك ن4)، فقياس Release يحتاج تعديلًا محليًا مؤقتًا (طلب مُدوَّن في OWNERSHIP).
